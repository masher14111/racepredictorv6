## Regression found while validating the rebuild (not in the first attempt's notes)

Cross-checking the candidate against the frozen baseline on shared
`(race_uid, horse_id, market_type)` keys found **501 frozen rows absent from
the candidate** — all `race_date == 2026-07-25` (the frozen baseline's own
cutoff day). Traced to `data/historical/betsp.parquet`: all 1,010 rows for
that day carry `position = NaN` under a single `fetched_at =
2026-09-18T22:29:20Z` — one blanket overwrite, timestamped the evening before
this session, most likely an uncorrected `scripts.fetch_results_window` re-run
(the D31/D32 bug pattern, just not caught for this specific day at the time).
The frozen baseline (D9-protected, untouched) still holds the correct WIN-market
positions for that day, proving the loss is real and post-dates the baseline's
own build.

**Repair** (`reports/improvement/06/repair_20260725_position_regression.py`,
backups at `data/audit/06/backups/*.pre_20260725_repair`): matched the 501
corrupted WIN rows to the frozen baseline's ground truth by
`(venue, race_time-minute, src_horse_id, market_type)` — market-type-EXACT.
Considered (then rejected) matching WITHOUT market_type: raw WIN/PLACE rows
for the same horse+race do carry an identical position when both are
independently resolved elsewhere (verified on 2026-07-20: 195/245 matched
pairs, 100% equal) — but the frozen baseline itself never has a
race_uid+horse_id resolved on both markets at once, so copying WIN's value
onto 07-25's PLACE rows would be an inference the one available ground truth
doesn't actually verify. Restored 501/505 WIN positions (4 have no frozen
match); PLACE stays null in the raw store, genuinely unresolved. Re-ran
`utils.normalizer.normalize(write=True)` to propagate the fix into
`data/unified_races.parquet` (offline merge of existing per-source stores, no
network). After the fix, `features/fuse.py`'s existing, documented
`_MARKET_SPECIFIC_COLS` cross-fill (position is deliberately NOT market-
specific — DESIGN.md) correctly broadcast the 501 restored WIN positions onto
their sibling PLACE rows in the derived matrix — 1,002 rows recovered
end-to-end, not 501, via the pipeline's own existing logic, not a manual copy.
Full suite after the repair: **2,324 passed** (step 05 baseline: 2,312; +12 new
tests this stage), same 1 pre-existing unrelated dateutil warning.

Thirteen OTHER pre-existing low-fill days were found during the same scan
(2023-12-31, 2024-03/04/07, 2025-01/04/07/08/10/11, 2026-03/04, 2026-06-12) —
all carry `fetched_at` timestamps from 2026-06-14 or 2026-07-27, both **before**
this improvement programme started (step 01, 2026-09-19). No frozen-baseline
ground truth exists for any of them (checked 2026-06-12 explicitly: 0 matching
rows). Left unrepaired and documented as a genuine pre-existing coverage gap,
not a regression this stage caused — repair would need a live re-scrape,
which stage 05 already found WAF-blocked in this environment.
