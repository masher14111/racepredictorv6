# 05 — Acquire current race declarations with source provenance

Date: 2026-09-19 (Claude Sonnet 5).
Status: DONE (engineering acceptance; no new model acceptance/forward-gate claim).

## Objective

Per `docs/improvement/prompts/05-current-declarations.md`: populate actual declared
jockey/trainer/weight/draw/age/sex/rating/equipment/runner-status where a legitimate
source provides them, keep provider IDs and fetched times distinct from canonical
identity, and repair the live "last-known-connections" behavior so today's declared
jockey is never silently invented from a previous run.

## What was found (rechecked against current code, not the dated review)

1. **`scraper/timeform/`** already exists as the app's racecard/enrichment provider —
   `scraper/timeform_historical.py::fetch()` fetches TODAY's declared card (Timeform
   serves dated index URLs as 500, but the bare index works for today), yet
   `scripts/refresh.py`'s live `_scrape()` never called it — only the 3 odds
   scrapers (livescorebet/boylesports/paddy_power) ran, and those "carry only
   horse + price" (confirmed in `features/builder.py`'s own docstring). So no
   declared jockey/trainer/draw/weight ever reached a live prediction; the only
   value that ever reached one was `_fill_last_known_connections`'s historical
   guess, presented identically to a real declaration.
2. `scraper/timeform/parser.py::RunRow` already had `horse_id`/`jockey_id`/
   `trainer_id` fields, but `parse_event` never populated them (always `None`) —
   confirmed on the real, previously-captured `data/historical/timeform.parquet`
   (28 rows, 2026-06-13): `jockey_id` 100% null, `trainer_name` 100% null.
   `trainer_name` itself was never parsed at all.
3. `features/fuse.py` already ranks `"timeform"` priority 3 (above `betsp`=2,
   live odds=1) and `utils/normalizer.py::_from_timeform` already derives a
   canonical name-based `horse_id`/`jockey_id`/`trainer_id` (matching odds
   sources' own name-derived ids) while preserving native ids under
   `src_horse_id`/`src_jockey_id`/`src_trainer_id` — the cross-source
   reconciliation design was already in place, just never fed live data.
4. Free (non-paywalled) racecard fields verified against the real saved fixture
   (`tests/scraper/timeform/fixtures/racecard_single.html`, a genuine captured
   York 2026-06-13 card): draw, weight (both a `data-weightsort` lbs total and
   the `10-9` stone-lb cell), age, official rating (OR), equipment code,
   colour+sex, and a native per-event id (`data-raceid`) all sit on free tbody
   attributes/cells; only `timeform_rating`/`pace_rating` are paywalled
   (confirmed already-handled: `None` unless `session_cookie` unlocks them).
5. **Found while tracing this stage's own evidence** (not in the dated review):
   `features/fuse.py::_drop_stale_live_rows` called
   `pd.to_datetime(df["fetched_at"], utc=True, errors="coerce")` over the WHOLE
   batch. pandas infers ONE timestamp format from the first non-null value; a
   batch mixing a whole-second `fetched_at` (a declared-card row) with a
   sub-second one (a live odds row) — normal once both sources run in the same
   refresh — parsed the differently-shaped row to `NaT`, which the age check
   then fail-closed as "unparseable -> too old", silently dropping a genuinely
   fresh row.

## What was done

1. **`scraper/timeform/parser.py`**: `parse_event` now extracts, from the free
   tier only: native `horse_id` (regex on the horse-profile link href),
   `jockey_id`/`trainer_id`/`draw`/`weight_lbs`/`timeform_race_id` (tbody
   `data-*` attributes), `trainer_name` (a cell the old parser never read),
   `age`, `official_rating`, `equipment`, `colour`/`sex` (pedigree cell), and a
   best-effort `runner_status` ("RUNNER"/"NON_RUNNER"). `timeform_rating`/
   `pace_rating` stay `None` in free mode, unchanged.
2. **`scraper/timeform/writer.py`**: `FINAL_COLUMNS` extended with the 9 new
   fields so they survive the parquet write.
3. **`utils/normalizer.py`**: `CANONICAL_COLUMNS` gained `src_race_id` (native
   per-event id — kept separate from the dead `race_id` column per D21) and the
   9 declared-card fields; `_from_timeform` maps `timeform_race_id` ->
   `src_race_id` and documents that a live (today, `position=null`) Timeform row
   reaching this adapter is a genuine current-card fact, not a fallback.
4. **`scripts/refresh.py`**: added `_scrape_declarations()` (best-effort, same
   pattern as the 3 odds scrapers) calling `scraper.timeform_historical.fetch()`
   inside `_scrape()`, so today's declared card is actually attempted on every
   daily refresh. A failure (WAF, no browser fallback, etc.) is logged and does
   not break the odds-only refresh.
5. **`features/builder.py::_fill_last_known_connections`**: now sets, per role
   (`jockey`/`trainer`), a `{role}_connections_source` column = `"declared"`
   (this row's own source already had it — e.g. today's fused Timeform row),
   `"historical_fallback"` (invented from the horse's own past runs, only when
   today's value was actually missing), or `"missing"` (neither available).
   `_derive_all` backfills/defaults this column to `"declared"` for real
   historical rows (training rows, and a live row's own prior runs) — those are
   actual past results, never a guess — which also keeps train/serve column
   parity (`test_train_and_inference_share_feature_columns`).
6. **`features/fuse.py::_drop_stale_live_rows`**: `pd.to_datetime(...,
   format="mixed")` so a batch mixing timestamp precisions across sources no
   longer silently drops a fresh row as unparseable.

## Limitations / unresolved

- **No fresh live declared card was actually captured this session** — the
  wiring (`scripts/refresh.py` -> `timeform_historical.fetch()`) is in place
  and unit-tested, but has never run end-to-end against a reachable Timeform
  response; it is proven against the real, previously-saved fixture only. The
  existing `data/historical/timeform.parquet` remains its June snapshot.
- **Non-runner detection is a best-effort heuristic** (`_is_non_runner` in
  `parser.py`), not verified against a real live withdrawal — the saved
  fixture predates any late scratching. Covered by a hand-constructed fixture
  in `test_parser.py`, honestly labelled as constructed, not captured.
- Draw/weight/OR/equipment/colour/sex/runner_status/src_race_id are new raw
  provenance columns, not yet added to `models/features.py`'s `FEATURE_COLS`
  — deliberately out of scope here (same additive-not-adopted pattern as
  D26/D27); a future step decides feature adoption.
- `jockey_connections_source`/`trainer_connections_source` are diagnostic
  metadata, not model features; no UI page currently surfaces them to a human
  operator — worth a follow-up if the app should visibly flag "guessed"
  connections rather than only carrying the flag internally.
- The hosted extraction trial (deepseek/deepseek-v4.1-flash) is unrelated to
  this stage's scope and was not touched.
