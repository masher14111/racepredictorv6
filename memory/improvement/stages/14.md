## Scope 1 — repaired boolean parsing / negation / ground-excuse misread

`llm/text_features.py::RegexBackend` previously used one ambiguous pattern
(`(?:un)?suited by the ... ground`) that matched a POSITIVE statement
("well suited by the soft ground" = no excuse) as if it were the excuse. Root
cause: `\bsuited` also matches inside `not suited`, so distinguishing "suited"
from its negation needs an explicit negator check, not an optional prefix.
Fixed with paired pattern lists per feature (`patterns` = explicit excuse
phrases incl. `unsuited`/`not suited`/`doesn't handle`; `negative_patterns` =
explicit "ground suits it" phrases, using `(?<!not )(?<!never )` lookbehind so
"not suited by..." cannot match the positive list). Negative (contradicting)
patterns are checked before positive ones, so a comment naming the ground and
explicitly denying the excuse resolves False, not a false positive.

Every feature now resolves to a tri-state `FeatureValue(value: bool|None,
evidence: str|None)`, not a bare bool: `None` = genuinely unmentioned
(unknown), never coerced to `False`. The regex backend itself never emits
`None` (a fixed-pattern matcher has no opinion beyond phrase presence/absence
— that is what its "False, no evidence" honestly means); unknown is the LLM
backend's job when a claim can't be grounded.

## Scope 2 — strict extraction schema + backend/failure visibility

`llm/text_features.py`:
- `TextFeature` now carries both `patterns` (excuse) and `negative_patterns`
  (explicit contradiction) per feature.
- `FeatureValue`/`ExtractionResult` dataclasses: every extraction carries the
  ACTUAL backend/model that produced it, `schema_version`, `prompt_version`
  (new, bumped on prompt wording change — regex has none), `is_fallback`, and
  `failure_reason`.
- `OllamaBackend.classify_detailed` requires each `true` claim's `evidence` to
  be an actual case-insensitive substring of the supplied text; an ungrounded
  claim is forced to unknown, not trusted. A response with zero usable
  entries returns `None` (triggers regex fallback); a response with SOME
  ungrounded entries still returns the grounded ones (a partial parse failure
  degrades only the affected features).
- **Bug fixed**: the pre-existing cache key was built from the *configured*
  backend name, so a failed Ollama call whose result came from the regex
  fallback was cached and later served back labelled `"ollama"` — silently
  misattributing a fallback result. `TextFeatureExtractor.extract_detailed`
  now checks and writes two separate cache slots (`{backend}` vs
  `{backend}_fallback_regex`) so a persistently-down Ollama server does not
  re-invoke the backend every call, and a working Ollama result can never be
  confused with a cached fallback (or vice versa).
- `extract()` (legacy bool-dict API) is kept for backward compatibility,
  built on `extract_detailed(...).as_bools()` (unknown -> False, documented as
  a lossy legacy view). No caller besides tests used it before this stage
  (`grep` confirmed) — nothing predictive changed.

## Scope 3 — append-only text archive

New `utils/storage/migrations.py::_migration_6` (same shared `data/races.db`
as `execution.snapshots.odds_snapshots`, migration 4): `text_archive` table,
keyed by content hash + source + `race_uid` + `runner_key` + `fetched_at`,
`RAISE(ABORT)` triggers forbidding UPDATE/DELETE (same construction as
`odds_snapshots`). `published_at` is nullable and NEVER backfilled from
`fetched_at`/`archived_at` — a source that gives no publish time stays unknown
forever, by construction (schema-level, not just discipline).

New `llm/text_archive.py::TextArchive`: `record()` (append), `history()` (all
versions, oldest first — nothing hidden), `as_of()` (point-in-time: filters on
`fetched_at <= as_of`, mirroring `SnapshotStore`'s `fetched_at`-based
contract, not on write-time `archived_at`, so a batched/delayed DB write can't
shift when text "was available"), `by_hash()`, `coverage()` (honest summary,
never a claimed corpus size).

`scraper/spotlight.py::scrape()` now archives every scraped comment
(`archive=True` default, `archive_store=` injectable for tests) via
`execution.race_facts.race_facts_key(venue, race_date)` as `race_uid` — the
same cross-source key format `execution/race_facts.py` already uses for
Sporting Life joins (chosen over `execution.snapshots.race_uid()`, which
expects a UTC-anchored input and would double-convert the already
local-minute `race_date` string `_local_minute` produces). Best-effort: one
bad row is logged and skipped, never aborts the batch. The existing
`data/spotlight.parquet` "latest view" cache (dedup-on-write) is UNCHANGED —
the archive is additive, not a replacement.

New `scripts/backfill_text_archive.py`: idempotent one-off import of the
existing `data/spotlight.parquet` into `text_archive`, preserving its real
`fetched_at` and leaving `published_at` unknown. Run this stage:
**243/243 rows archived, 21 races, 1 source, unknown_published_at=243** (see
`reports/improvement/14/backfill_output.txt`). Re-run confirmed idempotent
(still 243, not 486). `data/spotlight.parquet` itself untouched (read-only).

Predictive text features remain fully disabled (`llm.enabled: false` in
`config.yaml`, unchanged) — this stage is extraction/archive correctness only.
