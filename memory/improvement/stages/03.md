# 03 — Preserve WIN and PLACE market association when fusing data

Date: 2026-09-19 (Codex — GPT-6 Astra usage limit reached before step 01;
supervisor override routed this stage to Claude Sonnet 5 per D20, this session).
Status: DONE (engineering acceptance; no new model acceptance/forward-gate claim).

## Objective

Fix `features/fuse.py` so a runner's WIN and PLACE rows are never collapsed into
one row, per `docs/improvement/prompts/03-canonical-markets.md`. Re-verified the
prompt's own correction first: current data shows *mixed market rows*, not
duplicate runner keys.

## Root cause found (recheck, not the dated review's guess)

`features/fuse.py::_runner_key` grouped only on
`(race_date, venue, [race_time], horse_id)` — **omitting `market_type`**.
`data/unified_races.parquet` (raw, pre-fuse) has 324,170 of 326,407 runner-race
keys carrying **both** a WIN and a PLACE row (a normal full book); only 1,925
are WIN-only and 312 PLACE-only. The old groupby collapsed each runner's WIN
and PLACE rows into ONE row via `_first_valid` after a source-priority sort —
whichever market's row tie-broke first won **every** column, discarding the
other market's price/terms. This explains `data/features/training.parquet`'s
existing shape: 16,990 WIN-only races, 12,518 PLACE-only, only 4 with both —
the historical file already lost about half its per-market rows to this bug,
correlated at the race level (a race's rows share a source/import batch, so
they tended to tie-break the same way).

## What was done

1. **`features/fuse.py`**: `_runner_key` now appends `market_type` when present
   (`include_market=True` default; unchanged when the column is absent, so
   pre-existing tests without it are unaffected). A runner racing under both
   books now fuses to two rows, one per market, each keeping only that
   market's own source rows.
2. Added `_backfill_shared_attrs`: after per-market fusion, non-market columns
   (identity, ratings, form, `position` — see `_MARKET_SPECIFIC_COLS` for the
   excluded market/odds/terms/provenance set) are backfilled between a
   runner's WIN and PLACE row from whichever row has them, filling nulls only,
   never overwriting an existing value. Verified on real data: `jockey_id`,
   `trainer_id`, `going`, `horse_name`, `position` are identical across a
   runner's WIN/PLACE row wherever both are non-null (0 mismatches out of
   ~274k–324k comparable pairs) — the cross-fill is safe on this data.
   Implemented per-column, not as one multi-column call: grouping the whole
   shared-column block together crashed pyarrow's C++ layer on the all-null
   `null[pyarrow]`-dtype columns (`race_id`, `selection_id`, `market_id`,
   `validation_status`); an all-null column is now skipped (nothing to
   backfill either way). Also switched per-column fill from
   `groupby().transform(lambda s: s.ffill().bfill())` to
   `groupby().ffill()` + `.groupby().bfill()`: the lambda form calls Python
   once per group (~326k runner-race groups on the live matrix, x ~24 shared
   columns) and made a live rebuild hang for 15+ minutes; the vectorized
   cython ffill/bfill pair gives the identical result (groups are almost
   always size <=2) in seconds.
3. **`features/derive.py::_race_cols`**: now also appends `market_type` when
   present — a required companion fix. Every per-race grouping built on
   `_race_cols` (`add_odds_features`'s `field_size`/`market_rank`/
   `overround_norm_prob`, `add_rating_rank`, `horse_speed_rank`,
   `add_race_complexity`, `_market_movement.py`, `class_par_rank`) would
   otherwise rank/normalize a WIN row's implied probability against the PLACE
   book's prices and double `field_size`, once fuse.py stopped silently
   discarding one market's rows.
4. **`models/train.py`**: CatBoost's `train()` now restricts to
   `market_type == "WIN"` rows (when the column is present) before splitting,
   for **all** targets (won/placed_2/showed) — not per-target. Reasoning: live
   inference (`utils/market_validation.LIVE_SOURCES`) only ever emits
   `market_type=WIN`; `models/train_lgbm.py::_load_win_market` and
   `backtest/data.py::load_panel` already filter to WIN-only. Filtering
   placed_2/showed to the PLACE book instead (considered and rejected) would
   train those targets on a feature distribution (PLACE odds/terms) never seen
   at serving time — a worse defect than the one being fixed. This makes
   CatBoost's eligible population match LightGBM's exactly (prompt acceptance:
   "Both win-training lines use the same eligible-race rules").
5. Corrected `models/train_lgbm.py::_load_win_market`'s docstring, which
   claimed "PLACE duplicates every runner" — true of the raw data and now true
   again of a rebuilt matrix, but was NOT true of the existing (pre-fix)
   `training.parquet` (verified zero WIN/PLACE key overlap there — see below).
6. Adversarial tests added (`tests/features/test_fuse.py`, 11 new cases):
   one horse in WIN+PLACE, reordering invariance, place price never landing
   on the win row, shared-attribute backfill without price bleed, conflicting
   shared attributes preserved (fill-null-only), partial books, repeated
   races/venues, conflicting `race_id`. Plus `tests/features/test_derive.py`
   (market-isolation) and `tests/models/test_train.py` (WIN-population
   restriction, no-op when `market_type` is absent).

## Limitations / unresolved — load-bearing finding for step 04

**Un-collapsing WIN/PLACE rows exposes a second, separable defect in every
"trailing history" feature function** that assumes one row per runner per
race. These functions scan ALL rows of the derive-frame per entity
(`horse_id`/`jockey_id`/`trainer_id`) ordered by `race_date`; a runner now
legitimately has TWO rows per real race (WIN+PLACE), so:

- `add_days_since_last_run` — **verified corrupted**: a PLACE-market row
  computes its gap-from-previous-run against its own sibling WIN row (same
  `race_date`), yielding `0.0` instead of the true layoff gap. 2-race fixture:
  WIN rows correctly show `NaN, 31.0` days; PLACE rows show `0.0, 0.0`.
- `add_career_runs` — **verified corrupted**: counts double (each real race
  counted once per market row). Same fixture: `0,1,2,3` instead of `0,0,1,1`.
- `_freshness.py`'s `freshness_band` — downstream of the corrupted
  `days_since_last_run` (inherits the bug, not independent).
- `add_all_trailing_rates` / `_trailing_fast.windowed_rates`
  (`historical_win_rate`, `historical_place_rate`, `jockey_win_rate`,
  `trainer_win_rate`, `runs_in_window`) — the **rate** stays numerically
  correct (numerator and denominator double together), but `runs_in_window`
  doubles and `lookback_runs` now covers roughly half as many real races as
  configured — a real behavioural drift.
- Same run-doubling shape in `engine.add_speed_figures`'s `_speed_proxy`,
  `add_combo_win_rate`, `add_going_preference`, `add_course_suitability`,
  `add_distance_suitability`, `_trainer_form.py`, `_jockey_form.py`.
- `add_class_change` has the same shape, but `race_class` is 100% null today
  (CONTRACTS.md) — currently inert.

**Not fixed in this stage** — it is exactly `docs/improvement/prompts/
04-point-in-time-features.md`'s scope (prerequisites 02+03) and could not have
been surfaced before step 03 (every race had exactly one collapsed row until
now). A full fix (dedup history inputs by real race, broadcast back) spans
~10 functions across `derive.py`/`engine.py`/`_trainer_form.py`/
`_jockey_form.py` and needs step 10's retrain-and-compare tooling to verify
safely — out of this stage's scope. **`data/audit/03/training_market_fixed.
parquet` must NOT be used for any retrain until step 04 repairs this** — it
is correct for market/price/terms association but not for trailing-history
features. `data/features/training.parquet` (frozen artifact) is untouched.
