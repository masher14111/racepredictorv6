# 02 — Repair chronological splits throughout training and tuning

supervisor override routed this stage to Claude Sonnet 5 per D20, this session).
Status: DONE (engineering acceptance; no new model acceptance/forward-gate claim).

## Objective

Fix the row-count chronological-split defect stage 01 found in `models/train.py::_time_split`
(and the calibration/early-stop carve, and `models/tuner.py`'s tuning CV) so every fit/tune/
early-stop/calibration/test boundary is cut on whole `race_uid` groups, per
`docs/improvement/prompts/02-whole-race-splits.md`.

## What was done

1. New shared module `models/split_utils.py`:
   - `chronological_group_split(group_ids, order_keys, frac)` — single cut into
     (earlier, later) row-position arrays on whole-group boundaries; the "later" side
     is the smallest chronological suffix of groups whose row count is >= `frac` of
     total rows (rounds up to a whole race, never truncates mid-race).
   - `group_time_series_split(group_ids, order_keys, n_splits)` — walk-forward
     (expanding-window) K-fold generator over whole groups, the group-safe analogue
     of `sklearn.model_selection.TimeSeriesSplit`.
   - `race_group_overlap(...)` — audit/test helper counting shared group ids across
     partitions.
   - Both split functions: deterministic regardless of input row order (groups ordered
     by their own minimum `order_keys`, not row position); null/unknown group ids are
     each treated as their own singleton group (never silently merged); a single-group
     input cannot be split; empty input returns empty partitions instead of raising.
2. `models/train.py`:
   - `_time_split` now calls `chronological_group_split` (was: sort + `iloc[:split]`
     row-count cut). New `_group_carve` helper wraps the same primitive for the
     calibration and early-stop carves.
   - **Restructured the per-target loop**: calibration carve now happens *before*
     Optuna tuning (was: tuning ran on the full 80% train block, including rows that
     later became the calibration slice — a soft double-dip, not just a group-boundary
     bug). Tuning (`run_study`) now only ever sees `core_df` (train minus the
     calibration carve) and is passed `race_ids=core_df["race_uid"]`,
     `order_keys=core_df["race_date"]` for group-safe CV. Early-stop carve happens
     after tuning, on `core_df`, same primitive. Order is now strictly
     fit < early-stop < calibration < outer-test, chronologically, and disjoint by
     race_uid, for every target independently.
   - Added a fallback (`model.fit` without `eval_set`) for the edge case where a
     target's core reduces to a single race group (can't be split further for
     early-stopping) — logged as a warning, not a crash.
3. `models/tuner.py`: `run_study` gained optional `race_ids=`/`order_keys=` kwargs.
   New `_cv_splits` helper: uses `group_time_series_split` when both are supplied and
   there are enough unique races for the requested `cv_folds`; otherwise falls back to
   the original row-indexed `TimeSeriesSplit`, with a logged warning either way (no
   race identity supplied at all, or too few races to form the requested folds). Folds
   are computed once per study (not recomputed per trial).
4. `models/ensemble_experiment.py` (research script, not in the serving path): calibration
   carve now uses `_group_carve`; the stacker's out-of-fold base predictions
   (`_oof_base_preds`) now use `group_time_series_split` on `race_uid`/`race_date`
   instead of a plain row-indexed `TimeSeriesSplit` — this was explicitly named in the
   prompt scope ("ensemble out-of-fold predictions: time ordering alone does not
   preserve race groups").
5. `backtest/splitter.py` **audited, found already race-safe, not modified**:
   `walk_forward_folds`/`Fold` cut on whole calendar days via boolean masks on
   `race_date` (date-only per CONTRACTS.md), and every row of one race shares exactly
   one `race_date` value, so a day-level cut cannot split a race even when several
   races share that date. Added a regression test proving this holds with several
   distinct races sharing the boundary date
   (`tests/backtest/test_splitter.py::test_multiple_races_sharing_a_date_never_split_within_the_race`).
6. `scripts/calibration_report.py` had its own duplicate row-count `_time_split_test`
   (to "reproduce train.py's split" for reporting) — now imports and calls
   `models.train._time_split` directly so it can never silently drift from the real
   split train.py uses.
7. `docs/improvement/CONTRACTS.md` updated: the "complete-race splitting" section now
   records the fix, the re-verified zero-overlap evidence, and the `backtest/splitter.py`
   audit result.

## Limitations / unresolved

- No full production retrain/comparison was run — the prompt explicitly reserves that
  for step 10 ("Corrected frozen baselines and evaluation protocol"). This stage is
  engineering-only: the split contract is fixed and evidenced; whether the resulting
  model is *better* is not evaluated here and is not claimed.
- `group_time_series_split`'s fold sizes are only approximately equal (whole races vary
  in runner count, ~9 rows/race median but 1–31 range in the live data), unlike
  sklearn's row-exact `TimeSeriesSplit`. This is an inherent, accepted trade-off of
  group-safety, not a defect — documented in the module docstring.
  `_cv_splits` falls back to plain `TimeSeriesSplit` (logged warning) whenever there are
  fewer unique races than `cv_folds + 1`; this can only happen on very small/degenerate
  matrices (not the current production data, which has 29,512 races).
  `models/tuner.py`'s existing test suite still exercises this un-grouped fallback path
  directly (`tests/models/test_tuner.py`'s original tests pass no `race_ids`); this is
  intentional (documents the fallback), not an oversight.
- `models/ensemble_experiment.py::run()` (the full experiment, base-learner fitting +
  stacking) was not re-run end-to-end this stage (it retrains CatBoost/XGBoost/LogReg on
  ~200k rows — a genuine research-script rerun, out of this stage's engineering scope);
  only its now-repaired split/OOF logic was verified via `_prep`/`_oof_base_preds` being
  built on the same tested `split_utils` primitives, and via the full test suite passing.
- `audit/walkforward.py` was inspected (uses `backtest.splitter.walk_forward_folds`
  already, sorts by `race_date` only for deterministic row ordering, not for cutting) —
  no change needed, not separately re-tested beyond the existing suite.
