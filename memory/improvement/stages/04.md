# 04 — Repair independent features and historical feature invariance

Date: 2026-09-19 (Codex — GPT-6 Astra usage limit reached before step 01;
supervisor override routed this stage to Claude Sonnet 5 per D20, this session).
Status: DONE (engineering acceptance; no new model acceptance/forward-gate claim).

## Objective

Fix two verified defects per `docs/improvement/prompts/04-point-in-time-features.md`
and stage 03's load-bearing finding: (1) every `_trailing_fast`-based / hand-rolled
trailing feature double-counts (and can self-leak) now that a runner legitimately
carries WIN+PLACE rows per race (step 03); (2) `race_complexity`'s market-entropy
component sits inside a feature `models/features.py` lists as price-free/independent,
and its z-score is recomputed from whatever frame is passed in (dataset-global,
not train-fitted) — CONTRACTS.md's carried-over finding, rechecked here first.

## Root cause (rechecked, not assumed from the dated review)

1. `features/_trailing_fast.py`'s `windowed_rates`/`windowed_mean`, and the
   independent hand-rolled loops in `features/_trainer_form.py`/`_jockey_form.py`,
   treat every ROW as one event. Since step 03 gave a runner one row per market
   (WIN+PLACE) for the SAME real race, every trailing window double-counts a
   genuinely-prior real race, and (for the non-strict/positional paths) can let a
   row see its OWN market-sibling of the race being predicted as a spurious
   same-race "prior" — verified concretely on `days_since_last_run` (0.0 instead of
   the true gap) and `horse_career_runs` (counts doubled) in stage 03.
2. `features/engine.py::add_race_complexity` blends field_size/class/form/rating
   spread WITH `overround_norm_prob` entropy (market-derived) into one feature that
   `PRICE_FREE_FEATURE_COLS` (via `FEATURE_COLS` minus `PRICE_FEATURE_COLS`) lists as
   independent — confirmed by reading `models/features.py` directly. Its per-component
   `_zscore` also computes mean/std over whatever frame the caller passes (the full
   training matrix at train time; a small pruned recent-history+live frame at
   inference) — an admissible historical row's value depends on which OTHER rows
   share that call, including future rows appended later.
3. **Found while building this stage's own evidence** (not in the original dated
   review): a "fit a scale, then recompute the new feature on the training matrix"
   evidence-script shortcut recomputed race-group size on the ALREADY-
   `position.notna()`-filtered training frame instead of reusing the existing
   `field_size` column, silently UNDERCOUNTING any race with a non-runner/
   unresolved result. This exposed a genuine latent fragility in
   `_race_complexity_v2_raw_components` itself: it recomputed field size from
   scratch via its own groupby instead of reusing `derive.add_odds_features`'s
   already-correct, pre-filter column — safe inside `_derive_all` (always runs
   before any filter) but silently wrong if called again on a filtered subset,
   exactly what the evidence script did.

## What was done

1. **`features/_trailing_fast.py`**: added `_race_event_key` (prefers `race_uid`,
   falls back to `race_date+venue`, matching `derive._race_cols`) and
   `_dedupe_group_ids` (collapses a runner's same-real-race market-duplicate rows
   to one representative per (entity keys, race event), returning a group id array
   so a per-group result can be broadcast back via `result[group_id]`). Both
   `windowed_rates` and `windowed_mean` now dedupe before computing, then broadcast;
   both also normalize a bare string `keys` argument to a list. Added
   `windowed_win_rate_days` (shared day-windowed core) with the same collapse.
2. **`features/_trainer_form.py` / `_jockey_form.py`**: replaced their own
   independent, unfixed per-row day-window loops with `windowed_win_rate_days`,
   removing ~70 duplicated, buggy lines from each file. Public API unchanged.
3. **`features/derive.py`**: `add_days_since_last_run`, `add_career_runs`,
   `add_class_change` (currently inert — `race_class` is ~100% null in the
   TRAINING matrix; see Limitations for a raw-file nuance found this stage — fixed
   anyway per D25's explicit list) now collapse to one row per (entity, race event)
   via `_race_event_key`, computing the shift/cumsum on the deduplicated view and
   broadcasting back via a `MultiIndex` lookup.
4. **`features/_feature_scale.py`** (new): fit/save/load/apply a small JSON
   artifact of frozen `{mean, std, n}` per component. `load_scale()`/`save_scale()`
   resolve their default path from the module attribute at CALL time (not a bound
   default parameter), so tests can monkeypatch the path and every caller that omits
   `path` picks up the override.
5. **`features/engine.py`**: `add_race_complexity` (legacy) is UNCHANGED — every
   already-trained model bundle's `meta["feature_cols"]` (models/train.py) is bound
   to its exact current meaning (D9); redefining it in place would silently serve
   those bundles different inputs than they were trained on. Added, additively:
   `_race_complexity_v2_raw_components` (field_size + class/form/rating spread, NO
   market input; REUSES the existing `field_size` column instead of recounting —
   see root cause #3), `fit_race_complexity_v2_scale` (one row per race; its
   docstring now explicitly says fit from the FULL pre-label-filter matrix),
   `add_race_complexity_v2` (blends components standardized against a FROZEN scale
   instead of the call frame), and `add_race_market_entropy` (explicit
   market-assisted companion: Shannon entropy of `overround_norm_prob`).
6. **`features/builder.py::_derive_all`**: wired `add_race_complexity_v2` and
   `add_race_market_entropy` in ADDITIVELY, right after the legacy
   `add_race_complexity` call. Both new columns appear on both the training and
   inference matrix (train/serve parity).
7. **`models/features.py`**: added `CANDIDATE_INDEPENDENT_FEATURE_COLS =
   ["race_complexity_v2"]` and `CANDIDATE_MARKET_FEATURE_COLS =
   ["race_market_entropy"]` with a block comment explaining why `race_complexity`
   and `FEATURE_COLS`/`PRICE_FREE_FEATURE_COLS` are untouched. Adoption into a
   trained model is step 10's corrected-baseline retrain, not this step.
8. **Candidate artifact**: `reports/improvement/04/build_candidate_and_scale.py`
   rebuilds the SAME 8,000-race sample as stage 03's `rebuild_candidate.py` (same
   `random_state=42`) through the fixed pipeline, fits+saves
   `data/feature_artifacts/race_complexity_v2_scale.json`, and writes
   `data/audit/04/training_pit_fixed.parquet` (candidate; frozen
   `data/features/training.parquet` untouched).
9. **`reports/improvement/04/diagnose_determinism.py`** (new, kept as evidence):
   confirms `build_training_matrix` is deterministic across two identical calls —
   used to rule out a false "non-determinism" hypothesis before finding root cause #3.

## Acceptance check

- [x] **Appending later observations does not change earlier admissible feature
  values** — `tests/features/test_derive.py::
  test_days_since_last_run_append_future_race_does_not_change_earlier_rows`
  (synthetic, genuinely appends a later race) and
  `build_candidate_and_scale.py`'s append-invariance step (real data: diffs
  `race_complexity_v2`, `days_since_last_run`, `horse_career_runs`,
  `historical_win_rate`, `trainer_hot_strike_rate` after re-deriving with up to
  500 extra later races appended). **Limitation**: the 8,000-race random sample's
  own max date already equals the full dataset's max date, so 0 extra races were
  actually available to append this run — real-data evidence covers the
  "re-derive on the identical input is stable" case (which is how root cause #3
  was caught), not a genuine new-race append; the synthetic test is what actually
  proves the append-invariance property. 0 changed for every column either way.
- [x] **Independent features do not depend on odds, market shape or outcomes
  unavailable at the cutoff** — `race_complexity_v2` has no market-column input by
  construction, verified structurally by
  `test_race_complexity_v2_has_no_market_input` (mutating the market column leaves
  the output unchanged). The real-data correlation with market columns (up to
  ~0.48 with `market_rank`) printed in the log is EXPECTED and is not a leak: on
  today's data `race_complexity_v2` is dominated by `field_size` (the other 3
  components fit to `n=0` — see Limitations), and `market_rank`/`implied_prob`'s
  per-row distribution is mechanically bounded by field size regardless of any
  formula reading the market (a bigger field has runners at higher ranks and a
  smaller mean implied probability) — the same structural association the
  existing, already-independent `field_size` feature itself has always had.
- [x] **Feature schemas, required preprocessing and serving compatibility are
  explicit and tested** — `race_complexity_v2`/`race_market_entropy` are new,
  additive columns; `models/features.py`'s new `CANDIDATE_INDEPENDENT_
  FEATURE_COLS`/`CANDIDATE_MARKET_FEATURE_COLS` document them as not-yet-adopted;
  `models/predictor.py` binds each trained bundle to its own persisted
  `meta["feature_cols"]`, so extra columns are inert for existing bundles.

## Limitations / unresolved

- `race_complexity_v2`'s `race_class_std`/`recent_form_std`/`rating_std` components
  fit to `n=0` on the sampled TRAINING matrix — `race_class`/`recent_form_avg`/
  `timeform_rating` are ~0% populated among labelled rows. Raw-file nuance found
  this stage (not in CONTRACTS.md): the FULL `data/unified_races.parquet` has
  18/651,154 rows with a real `race_class` (all `timeform` source, 2026 dates) —
  CONTRACTS.md's "100% null" claim holds for the training matrix, not the raw
  file's absolute floor. Inert either way (components correctly drop out when
  all-null); flagged here rather than left for someone to rediscover.
- `tools/verify_trailing.py` (a stage-prior vectorization-equivalence script, not
  in the test suite) groups on the fused frame with no dedup, so it would now
  report mismatches against the fixed code — expected (proves the fix), not
  updated since it answers an already-closed question and isn't wired into CI.
- No production retrain/comparison run — step 10 owns that, same as stages 02/03;
  `data/audit/04/training_pit_fixed.parquet` is a candidate artifact only.
- `add_class_change`/`race_class` remains almost entirely null in training data
  today (fixed per D25 for correctness/consistency, but currently inert).
